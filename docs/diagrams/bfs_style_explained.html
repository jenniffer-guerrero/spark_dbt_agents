BFS-Style Expansion in This Project

The graph is bipartite: REL_ID nodes connect only to ID_KEY nodes. Expansion alternates REL_ID -> ID_KEY -> REL_ID until no new REL_ID appears.

What "BFS-style" means here

  • Start from an initial set called frontier.
  • Expand one hop level at a time (layer by layer).
  • Track all discovered nodes in visited.
  • At each iteration, only keep truly new nodes.
  • Stop when no new nodes are discovered.

How it maps to project code

In expand_rel_component:

via_id = frontier JOIN edges ON rel_id next_rel = via_id JOIN edges ON id_key new_rel = next_rel ANTI JOIN visited visited = visited UNION new_rel frontier = new_rel

expand_seed_pairs: What it does and how it differs

expand_seed_pairs runs a BFS-like traversal too, but the unit of traversal is a pair (seed_rel_id, rel_id) instead of just rel_id.

frontier = {(seed, seed)} visited = {(seed, seed)} via_id = (seed, frontier.rel_id) JOIN edges ON rel_id next_rel = (seed, via_id.id_key) JOIN edges ON id_key new_pairs = next_rel ANTI JOIN visited ON (seed_rel_id, rel_id) visited = visited UNION new_pairs frontier = new_pairs

Why it exists:

  • expand_rel_component answers: "Which rel_id nodes are impacted?"
  • expand_seed_pairs answers: "Which seeds can reach each impacted rel_id?"
  • Under the N->1 rule, each rel_id should resolve to a single active seed; reachability is still computed to validate and propagate mappings.

Relationship Between expand_rel_component and expand_seed_pairs

Stage A: Impact Expansion

Input: changed rel_id/seed triggers Function: expand_rel_component Output: impacted_rel_all Meaning: All rel_id nodes that might need output recomputation.

Stage B: Seed Reachability

Input: impacted active seeds + edges Function: expand_seed_pairs Output: (seed_rel_id, rel_id) pairs Meaning: All candidate seeds that can reach each impacted rel_id.

Stage C: Final Mapping

Input: seed pairs for impacted rel_id Apply fallback tie-breaker (defensive only): - latest_then_numeric OR - numeric_then_lex Output: One REL_ID_REGIE_KLANT per REL_ID.

Why this is useful in incremental ETL

  • A single changed edge can affect many nodes several hops away.
  • BFS-style traversal finds the full impacted connected component.
  • Only impacted REL_ID values are recomputed, not the whole output table.
