siebel_id_update — How It Works

A step-by-step visual guide explaining the incremental update logic: how the system detects what changed, which customers are affected, and how it updates only what it needs to.

★

The Big Picture — What does this module do?

Before diving into details, here is a high-level view of the whole process.

The goal: For every customer (rel_id), find which "master" customer (REL_ID_REGIE_KLANT) they belong to — and keep that mapping up to date every time the source data changes.
Why not recompute everything every time?
When data has millions of rows, rebuilding from scratch is expensive and slow. Instead, siebel_id_update detects only what changed and reprocesses only the affected customers — like patching a document instead of rewriting it from scratch.
1
Read fresh data from source tablesBuild the current list of connections and master customers.
2
Compare with the previous run's saved stateFind what was added or removed since last time.
3
Walk the graph to find all affected customersA connection change can ripple through a whole network.
4
Recompute only the affected areaAssign the correct master customer to each affected rel_id.
5
Merge and saveKeep unchanged rows, replace updated ones, save a snapshot for next time.
Key concepts explained simply
rel_id — Customer ID
A unique number that identifies one customer in the system.
id_key — Shared identifier
A number (like a bank account or contract ID) shared by two or more customers, creating a link between them.
seed / REL_ID_REGIE_KLANT — Master customer
A special customer flagged as a "master" (drc_bnk_f = 'Y'). All connected customers get assigned this master's ID.
edge — Connection / link
A single connection between a customer (rel_id) and a shared identifier (id_key). Like a friendship in a social network.
graph expansion (BFS) — Spreading through connections
Starting from one customer and following all connections step by step — like spreading news through a network of friends.
snapshot — Saved state
A copy of the data saved at the end of each run. Next time, it is used to detect what changed.

The freshly built data is compared against the saved state from the previous run. Only differences matter.

Three types of changes detected
1. Changed edges
Connections between customers and shared IDs that were added or removed.
→ The customers on both ends of that connection need to be re-evaluated.
2. Added / removed seeds (master customers)
A customer was promoted to master, or a master was demoted.
→ Every customer in that master's network needs a new assignment.
3. Rows linked to a removed seed
Customers that were previously mapped to a master that no longer exists.
→ They lose their assignment and may receive a new one, or be dropped.
How the comparison works (anti-join / left_anti):
Take all rows from the current data that do not appear in the previous data → these are added.
Take all rows from the previous data that do not appear in the current data → these are removed.

Walking the Graph — Finding Every Affected Customer

A change in one connection can ripple through an entire network. This step finds all customers that need to be updated.

The problem: A new connection (edge) was added for customer 1004. But 1004 shares IKB-99 with customer 1002, who shares SBL-55 with the seed 1001. The whole chain is affected.
BFS — Breadth-First Search (wave expansion)
0 Start: changed rel_ids = {1004}

SBL-55 → 1001 (new!)
✓ No new nodes found. Stop.
Impacted: {1001, 1002, 1004}
Max 40 iterations. If the graph is huge and still expanding at step 40, the run is flagged as truncated and an error is raised (safety net).
4

Recomputing the Affected Area — Assigning a Master to Each Customer

For all impacted customers, the system walks the graph again — but this time it tracks which seed (master) it started from.

Goal: For each impacted rel_id, find all the seeds that can reach it through the network. Then pick one winner using a deterministic rule (same input always gives same output).

How the winner is chosen (tie-breaker rule)
Option A (default): numeric_then_lex
1. Try to convert each seed ID to a number.
2. The smallest number wins.
3. If none are numeric, the alphabetically smallest seed ID wins.

Example: seeds {1001, 999, "ABX-5"} → 999 wins (smallest number)
Option B: latest_then_numeric
1. The seed with the most recent activation date wins.
2. Ties broken by smallest number, then alphabetically.

Example: seeds {1001 (2023), 999 (2024)} → 999 wins (most recent)
Why deterministic?
Running the same data twice must always produce the same result. A deterministic rule (like "smallest number") guarantees this — there is no randomness.

How the merge works:

1. Take the previous output and remove all rows whose REL_ID is in the impacted set.

2. Add the recomputed rows for those impacted customers.

3. Final filter: keep only rows whose assigned master (REL_ID_REGIE_KLANT) is still an active seed today. Rows assigned to a master that no longer exists are dropped.
Why drop rows when the seed disappears?
If a customer was assigned to master "1001" and "1001" is no longer flagged as a master customer (drc_bnk_f changed from Y to N), then the assignment is no longer valid. Those rows are removed from the output entirely.
Zero waste: customers with no changes are never touched — their rows pass through unchanged.

Saving Results Safely — The Staging Table Swap

Writing directly to a live table is risky. Instead, the system uses a "swap" technique to make writes atomic and safe.

The problem with direct writes: On Parquet-backed tables (like in Spark/Databricks), SQL UPDATE is not always supported. Even when it is, writing directly to a live table risks partial writes if something goes wrong mid-way.

7

Safety Features — Checkpoints, Truncation Guard & Audit Log

The system has several built-in safety nets to handle large data and catch problems early.

💾
Checkpoints (memory management)

During graph expansion, Spark builds up long chains of operations in memory (called lineage). If the graph is large, this can cause memory issues.

Checkpoints save intermediate results to disk every 2 iterations, breaking the chain. Think of it as pressing "Save" while writing a long document.
🛑
Truncation guard (max_iter = 40)

Graph expansion stops after 40 iterations maximum. If the graph is still growing at that point, it means the network is unusually large or there may be an error in the data.

When this happens, the run raises an error (unless fail_on_incomplete = False), ensuring bad results never get silently written.
📋
Run audit log

After every run, a summary row is appended to state_db.run_audit. It records what happened so the team can investigate trends or problems later.

First Run vs Incremental Run — Two Modes

The system behaves differently on the very first run (when there is no saved state yet) versus all subsequent runs.

Aspect First Run (empty snapshots) Incremental Run (snapshots exist)
Previous state None — all snapshot tables are empty Loaded from state_db snapshots
Impacted set ALL rel_ids in the current data Only the rel_ids affected by changes
Work done Full recompute — equivalent to siebel_id_origin Partial recompute — only the affected area
Speed Slow (processes everything) Fast (processes only what changed)
After run Snapshots are written for the first time Snapshots are updated with current state
How the system detects "first run": It checks if all three snapshot tables (edge_snapshot, seed_snapshot, seed_membership) are empty. If so, it treats every row as impacted.
